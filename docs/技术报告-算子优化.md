## 2. 摘要

本阶段工作在 **InfiniCore + 九齿（NineToothed）** 内重写并融合了 MiniMax-H3 DiT 的全部非 GEMM 计算算子，并在 InfiniCore 的算子接口层把 BF16 GEMM 接到厂商 BLAS 的确定性算法上。所有新增计算算子都用九齿 DSL 编写、经九齿 → Triton → hsaco 生成，没有手写 HIP/Triton kernel，也没有在九齿内部转调现成计算库。

在开发环境（海光 K100-AI ×4，DTK 25.04.2）上，单步 DiT 基准（真实捕获输入，50 个 block 完整前向）从 **4.935 s** 降到 **4.805 s**；完整 FL2VA 生成中 DiT 每步从 9 月成果的 **5.105 s** 降到 **4.839 s**，计分段 `generation.pipeline_total` 从 9 月基线的 **290.0 s** 降到 **246.0 s**，相对官方 PyTorch 参考实现（同机 1038.2 s）加速 **4.22×**。除显式标注的两项（VAE tile 合批、hipBLASLt 换算法，后者未采用）外，其余改动均与优化前**逐位一致**（bitwise identical）。

针对赛方提供的 **海光 Z100（gfx906）** 环境，本报告给出了算子移植方案、构建脚本与算子级测试框架；该环境上的实测数据见第 7 节（待在该环境上执行后填入）。

该平台与 K100-AI 的三个关键差异，直接决定了移植方案：

1. **上游 Triton 不支持 gfx906。** PyPI 的 triton 3.1.0 在该架构上编译即失败：
   `loc(...): error: unsupported target: 'gfx906'`（其 AMD 后端只覆盖 CDNA 的 gfx908/90a/94x 与 RDNA 系列）。因此**九齿（经九齿 → Triton → hsaco）在本环境暂时无法生成内核**，K100 阶段的融合算子无法直接在 Z100 上编译。要在 Z100 上复用这些算子，需要海光 DAS 提供的、支持 gfx906 的 triton 构建。
2. **hipBLASLt 没有 gfx906 内核。** 镜像内 `/opt/dtk/lib/hipblaslt/library/` 只有 `TensileLibrary_gfx928.*`，而 rocBLAS 有完整的 gfx906 Tensile 库。因此 K100 上采用的「cuBLASLt/hipBLASLt 显式启发式算法」路径在 Z100 上会在描述符创建阶段失败并自动退回 rocBLAS（代码已有该退路），GEMM 优化在本平台需改从 rocBLAS 侧入手。
3. **无 MFMA、无原生 BF16。** gfx906 属 GCN5/Vega 20，没有矩阵核心，BF16 由编译器转换实现，因此算子需同时评估 FP16 与 BF16（本仓库的算子生成器已参数化 `dtype`）。
4. **显存 16 GiB ×2**，不足以承载 50 层 DiT 的完整权重（SP4 下每卡约 48 GB），与赛方"初赛小卡只做算子层优化"的安排一致。

## 5. 优化思路

### 5.1 逐元素算子：按"参考舍入边界"融合

H3 的参考实现（Diffusers + PyTorch 2.5，BF16）在 RMSNorm、AdaLN、门控残差、SwiGLU 的**每一个中间量**上都做一次 BF16 舍入。该模型对舍入级扰动高度敏感（两种数学等价实现在第 0 步输出即有约 3% 相对差，49 步后视频轨迹明显分叉），因此融合算子不能做"一次舍入"的常规优化，而要在九齿 DSL 里把每一步的 `.to(bf16)` 显式写出来。这样做的收益是消除中间张量的全局内存往返，同时保证输出与未融合版本**逐位一致**：

- `h3_gated_residual_rms_modulate`：把"门控残差 → RMSNorm → AdaLN"三步合成一个 kernel，中间的 `residual` 与 `normalized` 不再落地（H3 的 hidden 为 5376，SP4 下每块这两个张量各约 60 MB）。
- `h3_qk_norm_rope`：把 q/k 的逐头 RMSNorm、三轴 RoPE 与"按目标卡打包"的重排合成一个 kernel，直接写进 all-to-all 的发送缓冲，省掉三次读写。
- 分块形状与 warp 数按架构实测选取：SwiGLU 由 16×256 瓦片改为"每程序一条 1024 宽行片、4 warp"（1.25 ms → 0.885 ms，逐位一致）；`h3_qk_norm_rope` 由 2 warp 改为"每程序 1 token、1 warp"（0.442 ms → 0.391 ms，逐位一致）。两者都是在同一算子语义下只改并行映射。

### 5.2 把 Python 侧残留的 torch 计算收回 InfiniCore/九齿

DiT 的 RoPE cos/sin 表原先在 Python 里用 torch 计算。按赛题要求，Qwen3-VL 与 DiT 的计算必须走 InfiniCore 或九齿，故改为：

- 16 个频率幂 `theta^(2k/32)` 用 InfiniCore 已有算子 `float_power`（设备 `powf`，每卡每进程只算一次）；
- 逐 token 的 `cos`/`sin` 用新增九齿算子 `h3_rope_cache`，内部通过 `ninetoothed.language.libdevice` 调用设备数学库的 `cos`/`sin`（与 PyTorch 同一套 ocml 实现）。

实测在捕获的真实位置、整数/均匀/细粒度随机位置共 6 组输入上与原 torch 实现**逐位一致**，整段视频逐字节相同。Qwen3-VL 与 DiT 的三轴位置下标也改为在主机上用整数运算生成后一次拷贝，正式路径上不再有 torch 的设备 kernel。

### 5.3 注意力

DiT 的全注意力使用 InfiniCore 的海光 flash attention 适配（经 `at::scaled_dot_product_attention`，赛方 Q&A 明确允许且鼓励）。九齿版本 `h3_full_attention` 作为自研实现保留并持续调优：Q 块提到 K/V 循环外，分块配置离线调优后写入 `configs/<arch>/attention.json`。开发环境上厂商 kernel 约 96 TFLOPS、九齿版本约 70 TFLOPS，故默认走厂商实现（`INFINICORE_HYGON_MHA=aten`，`ninetoothed` 可切回自研）。

实测厂商 FA 的效率与单次调用的头数基本无关（7 头 95.6 TFLOPS、14 头 96.4 TFLOPS），这支撑了"按头分组 + 通信重叠"的并行方案不会损失注意力效率。

### 5.4 GEMM 接入层

InfiniCore 的 BF16 GEMM 改走 cuBLASLt 兼容 API（DTK 映射到 hipBLASLt），每个形状在描述符创建时显式选定一次启发式算法，并在每次取 handle 时设置确定性模式（禁用 atomics split-K），使每个 GEMM 逐位可复现。相对 rocBLAS 每步快约 3%。

进一步用 `hipblaslt_ext::getAllAlgos` 枚举了全部 217 个算法（其中 72 个支持本形状）逐一计时：启发式给出的算法已落在最快一档内，仅 down 投影形状还有约 5% 余量（折合每步 0.4%）且结果不逐位一致，故**未采用**按形状候选表（代码保留为诊断工具 `tools/tune_gemm_lt.py`，默认不启用）。

### 5.5 算子之外的调度优化（同属本阶段成果，便于复现端到端数字）

- **批量 AdaLN**：原先 50 个 block 每步各做一次列并行小 GEMM + 一次同步 all-gather，并把调制向量按 token gather 成 `[tokens, 6×hidden]` 大表（SP4 下每块约 370 MB）。改为前向开始时一次算完全部 block 的本卡投影、只做一次 all-gather；本卡 token 按"共用同一调制行"分段，融合算子在步长为 0 的广播视图上按段执行。调制向量不再落地为大表，`h3_gated_residual_rms_modulate` 的实测耗时随之从 0.95 ms 降到 0.47 ms；单步逐位一致，4.940 s → 4.835 s。
- **计时外开销**：视频帧转 PIL 的像素转换移到设备上做（同样的 FP32 乘 255、就近偶数舍入、uint8 转换），像素逐位一致，计时外开销 4.76 s → 0.97 s。
- **加载期预热**：用 448×448 合成输入在加载阶段跑一次 2 步小生成（输出丢弃，不缓存任何与输入相关的数据），把惰性加载与首次调用开销移出计分段。

## 6. 性能与正确性

### 6.1 单个 DiT block 的 kernel 耗时（K100-AI ×4，hipprof，S=22901，SP4）

| kernel | 每 block 调用次数 | 耗时 |
|---|---:|---:|
| 厂商 flash attention | 2（每卡 14 头分 2 组） | 2 × 19.3–19.8 ms |
| GEMM：QKV（按头组拆 2 次） | 2 | 5.8 + 6.4 ms |
| GEMM：out / gate_up / down | 各 1 | 3.6 / 17.0 / 8.7 ms |
| `h3_qk_norm_rope` | 4（q/k × 2 头组） | 4 × 0.47–0.58 ms |
| `h3_swiglu_exact` | 1 | 1.47 ms（旧 16×256 分块；新分块单算子实测 0.885 ms） |
| `h3_gated_residual_rms_modulate_exact` | 1 | 0.47 ms |
| `h3_gated_residual_exact` | 1 | 0.37–0.39 ms |
| `h3_rms_modulate_exact` | 1 | 0.36 ms |

每 block 约 96 ms，其中 GEMM + FA 约 81 ms（GEMM 105–114 TFLOPS、FA 约 96 TFLOPS，均贴近第 3.1 节实测上限），逐元素算子合计约 5 ms，其余为未被计算掩盖的 all-to-all（本开发机 DCU0 互联带宽偏低，约 6 ms；赛方机器无此问题）与启动空隙。上表取自 hipprof 单步时间线（SwiGLU 分块改动前）。

### 6.2 端到端（同一用例、同一台 K100-AI ×4）

| 版本 | DiT 每步（完整运行） | 单步基准 | `generation.pipeline_total` | 端到端 |

## 7. Z100（gfx906）移植

### 7.1 当前环境阻塞：Pod 内 GPU 不可用（需平台侧处理）

2026-10-13 在分配到的 Pod 上实测，**该容器内无法执行任何 GPU 计算**，证据链如下：

| 检查 | 结果 |
|---|---|
| `hy-smi` | 能看到 2 张卡（46 ℃、450 W 功耗上限、显存 0%），卡本身健康 |
| `/dev/kfd`、`/dev/dri/{card3,card4,renderD130,renderD131}` | 都已透传，root 可访问 |
| `rocminfo` | **GPU agent 数 = 0**（只有 4 个 CPU agent），`DMAbuf Support: NO` |
| `torch.cuda.device_count()` | 返回 2（走 SMI 枚举，不代表可用） |
| `torch.zeros(4, device="cuda")` | **段错误** |
| 镜像内 DTK | 仅 `/opt/dtk-26.04`（`/opt/dtk` 指向它） |
| 宿主驱动 | `/sys/module/hydcu/version` = **6.2.31** |
| 运行时告警 | `please install the latest driver(version >= 6.3.15)` |

即：镜像的 DTK 26.04 运行时要求驱动 ≥ 6.3.15，而该节点驱动为 6.2.31，HSA 运行时因此枚举不到 GPU agent，任何设备分配都会崩。赛方指南中"已验证环境"报告的是 HIP 6.3.26093，说明其验证节点的驱动较新。

**需要平台侧处理（二选一）**：
1. 在控制台重建/重启容器，使其调度到驱动 ≥ 6.3.15 的节点；或
2. 选用与该节点驱动（6.2.x）匹配的基础镜像（DTK 24.04 / 25.04 时期的 PyTorch 镜像）。若该镜像自带海光 DAS 的 triton，还可同时解决下文的九齿内核问题。

本阶段在该环境下仍然完成并验证的部分：**InfiniCore 为 gfx906 的编译与安装全部通过**（C++ 库、Python 扩展、可编辑安装），编译期的架构适配没有问题；`import infinicore` 的崩溃点经 gdb 定位在
`context::getDeviceCount` → `infiniopCreateHandle` → `device::hygon::Handle` → `cublasCreate_v2` → `hipblasCreate` → `rocblas_create_handle` → `hipMalloc`（崩在 `libgalaxyhip.so.5`），与上述驱动问题同源，**不是代码问题**。

| 问题 | 结论 / 处理 |
|---|---|
| 九齿内核能否在 gfx906 生成 | **暂不能**：上游 Triton 的 AMD 后端报 `unsupported target: 'gfx906'`。需要海光 DAS 的 triton 构建（支持 gfx906、匹配 DTK 26.04 / Python 3.11）。本仓库已备好 `tools/probe_triton_arch.py` 作为平台冒烟测试：一旦换上可用的 triton，它会逐一验证 elementwise / reduction / `tl.dot` 在 FP32、FP16、BF16 下的结果误差。 |
| 算子源码是否需要改 | 不需要改算术，只需按架构重新生成：`scripts/build_h3_attention.py --archs gfx906`，分块配置 `configs/gfx906/attention.json`。所有生成器已参数化 `dtype`（BF16 / FP16）与分块形状、warp 数。 |
| GEMM 优化 | K100 的 hipBLASLt 显式算法选择在 gfx906 无内核可用，自动退回 rocBLAS；本平台应从 rocBLAS 侧（按形状选 solution）入手。 |
| 可立即测量的基线 | `tools/bench_infinicore_ops.py`：直接测 InfiniCore 自身的算子实现（rms_norm、swiglu、matmul、mha、timestep_embedding、embedding）对 PyTorch 参考的正确性与耗时，**不依赖 triton**，因此在 Z100 上可用。 |

## 10. 合规说明

- 新增的模型计算算子全部用九齿 DSL 编写，经九齿 → Triton → hsaco 生成；没有手写 Triton/HIP/CUDA kernel，九齿内部没有转调 flash-attn / hipBLASLt 等现成计算 kernel。
- DiT 注意力使用 InfiniCore 的海光 flash attention 适配（赛方 Q&A 明确允许）。
- 未修改权重、计算语义、测试数据与评测程序；未做量化、低秩近似、稀疏/窗口注意力、步数或分辨率缩减、跨步特征复用、跨用例缓存。
